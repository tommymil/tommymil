# Audyt projektu Lesson Runner — 27.07.2026

Zakres: dokumentacja (`PLAN.md`, `README.md`, `PROJEKT_W_TRAKCIE`, `CLAUDE.md`), backend
(`backend/**`), frontend (`frontend/lesson-runner-web/**`), konfiguracja uruchomieniowa
(`docker-compose.yml`, `Dockerfile`, `appsettings*`).

Uwaga o weryfikacji: w środowisku audytu nie było SDK .NET, a testy Vitest nie dały się uruchomić
(node_modules zbudowane pod Windows). Zweryfikowano natomiast **`tsc --noEmit` — przechodzi bez
błędów**. Testy backendu (122) i frontendu (109) należy przepuścić lokalnie przed wdrożeniem
poprawek z tego dokumentu.

Ogólna ocena: architektura jest spójna i dojrzała — Clean Architecture po stronie backendu,
konsekwentny podział MVVM-like we frontendzie, migracje EF, audyt, backup, health check, Docker.
Nie znalazłem błędów kompilacji ani strukturalnych. Problemy leżą w warstwie **logiki
powiadomień, autoryzacji ról i utwardzenia produkcyjnego** — czyli dokładnie tam, gdzie boli tuż
przed wyjściem na produkcję.

## 1. Błędy krytyczne (naprawić przed produkcją)

### 1.1 Fałszywe e-maile o nieobecności do wszystkich rodziców przy starcie zajęć

**Plik:** `backend/LessonRunner.Application/Groups/SessionService.cs`, linie 76–84.

`StartAsync` tworzy wiersze obecności z `Present = false` dla **wszystkich** zapisanych dzieci
(to prawidłowe — lista startuje niezaznaczona), a zaraz potem wywołuje:

```csharp
var absentParticipantIds = records.Where(record => !record.Present)...
await notificationService.NotifyAbsencesAsync(sessionId, absentParticipantIds, cancellationToken);
```

Skutek: w momencie kliknięcia „Start” **każdy opiekun ze zgodą RODO i adresem e-mail dostaje
powiadomienie, że dziecko było nieobecne** — zanim instruktor w ogóle odhaczył listę.
Dodatkowo klucz deduplikacji `absence:{sessionId}:{participantId}` blokuje późniejsze wysyłki,
więc korekta już nie pójdzie, a `SaveAttendanceAsync` w ogóle nie wywołuje powiadomień
(jedyne miejsce wywołania w całym repo to `SessionService.cs:83`).

Obecnie ratuje Was tylko `Smtp:Mode = "Log"`. Po przełączeniu na realny SMTP to wybuchnie
przy pierwszych zajęciach.

**Poprawka:** przenieść wywołanie `NotifyAbsencesAsync` z `StartAsync` do `SaveAttendanceAsync`
(po zapisaniu rekordów), i wysyłać tylko dla tych, którzy po zapisie mają `Present == false`.
Docelowo najlepiej dopiero przy `FinishAsync`, żeby ponowna edycja listy nie generowała maili.

### 1.2 Rodzic ma dostęp do całej biblioteki konspektów

**Plik:** `backend/LessonRunner.Api/Program.cs`, linia 186.

```csharp
var lessons = app.MapGroup("/api/lessons").WithTags("Lessons").RequireAuthorization();
```

`RequireAuthorization()` bez polityki oznacza „dowolny zalogowany” — czyli także rola `Parent`.
Zalogowany rodzic może wywołać `GET /api/lessons` oraz `GET /api/lessons/{id}` i pobrać pełną
treść konspektów razem z **notatkami instruktora, wskazówkami i scenariuszem prowadzenia**.
To samo dotyczy `POST/PUT /api/lessons/{id}/run-session` (linie 263, 282) oraz
`GET /api/calendar` (linia 1112 — zwraca pustkę dla rodzica, ale endpoint jest otwarty).

**Poprawka:** dodać politykę `StaffOnly` (`RequireRole(Admin, Instructor)`) i użyć jej dla grup
`/api/lessons`, `/api/schedule`, `/api/calendar`.

### 1.3 Dezaktywacja wszystkich administratorów = trwałe zablokowanie systemu

**Plik:** `backend/LessonRunner.Infrastructure/Auth/EfUserRepository.cs`, linie 99–103.

```csharp
return dbContext.Users.AnyAsync(user => user.Role == adminRole, cancellationToken);
```

`HasAnyAdminAsync` nie sprawdza `IsActive`. Jeżeli admin dezaktywuje samego siebie (albo ostatnie
aktywne konto admina), to:

- zalogować się nie może nikt (`AuthService` blokuje `!user.IsActive`),
- `BootstrapAdminAsync` nie odtworzy konta, bo widzi „jakiegoś” admina w tabeli.

Wyjście tylko przez ręczną edycję bazy.

**Poprawka:** `AnyAsync(user => user.Role == adminRole && user.IsActive)` plus twarda walidacja
w `UserAdminService.SetActiveAsync` — nie pozwól zdezaktywować ostatniego aktywnego admina
ani konta, na którym się właśnie pracuje.

## 2. Bezpieczeństwo (ważne przy danych dzieci)

### 2.1 Katalog `/uploads` jest w pełni publiczny

**Plik:** `Program.cs`, linie 117–124.

`UseStaticFiles` z `PhysicalFileProvider` jest zamontowany **przed** `UseAuthentication()` i bez
żadnej autoryzacji. Każdy plik wgrany do lekcji (obrazy, PDF-y, paczki `.sb3`/`.zip`) jest dostępny
pod `http://serwer/uploads/<guid>.png` dla dowolnej osoby z internetu. Nazwy są GUID-ami, więc nie
da się ich zgadnąć, ale to „security by obscurity” — link raz wysłany rodzicowi działa wiecznie
i dla każdego.

**Poprawka:** albo serwować pliki przez endpoint z `RequireAuthorization()` (analogicznie do
`/download/lesson-files/{token}`), albo przynajmniej ustawić `Cache-Control: private, no-store`
i świadomie zaakceptować ryzyko w polityce prywatności.

### 2.2 Brak limitowania prób logowania

`POST /api/auth/login` (`Program.cs:1225`) nie ma żadnego throttlingu — w całym Api nie występuje
`AddRateLimiter`. Hasła mają minimum 8 znaków, hash to PBKDF2, ale nic nie powstrzymuje ataku
słownikowego. Audyt zapisuje nieudane próby, tylko nikt na nie nie reaguje.

**Poprawka:** wbudowany `AddRateLimiter` (np. 5 prób / 5 min / IP + e-mail) na `/api/auth/*`.

### 2.3 Token JWT nie da się unieważnić

Token żyje 12 h (`Jwt:ExpiryMinutes = 720`), a autoryzacja opiera się wyłącznie na claimach
(`GET /api/auth/me`, `Program.cs:1242` — czyta rolę z tokenu, nie z bazy). Skutki:

- dezaktywacja konta działa dopiero po wygaśnięciu tokenu (do 12 h),
- zmiana roli użytkownika nie propaguje się do aktywnej sesji,
- reset hasła przez admina nie wylogowuje intruza.

**Poprawka minimalna:** dodać do `User` pole `SecurityStamp`/`TokensValidFrom`, wstawiać je do
tokenu i sprawdzać w zdarzeniu `OnTokenValidated`; przy dezaktywacji / zmianie hasła — przestawiać.

### 2.4 Dane logowania developerskie na ekranie logowania

**Plik:** `frontend/lesson-runner-web/src/pages/LoginPage.tsx`, linia 92.

```
Konta developerskie: admin@lessonrunner.local / admin12345, instructor@... / teacher12345
```

Renderowane bezwarunkowo — trafi do builda produkcyjnego. Jeżeli ktoś zapomni skasować konta
seed (a seed odpala się tylko w Development, więc zwykle ich nie będzie), to i tak zostaje
podpowiedź konwencji nazewnictwa kont.

**Poprawka:** owinąć w `import.meta.env.DEV`.

### 2.5 Sekrety w `docker-compose.yml`

Plik zawiera jawnie `Jwt__SigningKey`, hasło do PostgreSQL i `BOOTSTRAP_ADMIN_PASSWORD:
admin12345`. Jako plik developerski jest OK, ale jest to jednocześnie jedyny opisany sposób
uruchomienia produkcyjnego i łatwo go skopiować na serwer 1:1.

**Poprawka:** przenieść do `.env` (nieśledzonego przez git), dodać wariant
`docker-compose.prod.yml` bez wartości domyślnych, wymusić start z zewnętrznych zmiennych.

### 2.6 `/health` ujawnia komunikat błędu bazy

`Program.cs:126–154` — endpoint anonimowy, a przy awarii zwraca `ex.Message`, czyli potencjalnie
connection string, nazwę hosta bazy czy ścieżkę pliku.

**Poprawka:** publicznie zwracać wyłącznie `status`, szczegóły logować przez Serilog.

### 2.7 Drobne

- **`/download/lesson-files/{token}`** (`Program.cs:156`) — anonimowy i przy każdym pobraniu
  ładuje **wszystkie lekcje** z bazy, żeby znaleźć jeden plik. Do przepisania na indeksowany lookup.
- **Token w `localStorage`** (`AuthContext.tsx`) — podatny na XSS. Przy tej klasie aplikacji
  akceptowalne, ale warto to świadomie zapisać.
- **CSV injection** — `EscapeCsv` (`GroupService.cs:826`) poprawnie escapuje cudzysłowy i średniki,
  ale nie chroni przed formułami Excela (`=`, `+`, `-`, `@` na początku komórki). Nazwiska dzieci
  wpisuje admin, więc ryzyko jest niskie — dodanie apostrofu przed takimi wartościami to jedna linia.

## 3. Błędy funkcjonalne i logiczne

### 3.1 Numeracja faktur — kolizje i brak ciągłości rocznej

**Plik:** `backend/LessonRunner.Application/Billing/BillingService.cs`, linie 135 i 326–327.

```csharp
Number = NextInvoiceNumber(invoices.Count + 1);
// FV/{rok}/{sekwencja:D5}
```

Sekwencja to **globalna liczba wszystkich faktur**, nie licznik roczny. Efekty:

- numeracja nie resetuje się 1 stycznia (2027 zaczyna się od `FV/2027/00041`),
- dwie równoległe faktury dostaną ten sam numer → naruszenie unikalnego indeksu → HTTP 500,
- polskie przepisy wymagają numeracji ciągłej w obrębie okresu — obecny schemat jest formalnie
  wątpliwy.

**Poprawka:** licznik per rok, wyznaczany transakcyjnie (osobna tabela sekwencji albo
`MAX(numer)` w transakcji z retry na konflikt unikalności).

### 3.2 Instruktor na zastępstwie nie widzi zajęć w kalendarzu

`SchedulingService.GetCalendarAsync` (linia 96) filtruje przez
`groupRepository.ListByInstructorAsync(userId)`, a to zapytanie
(`EfGroupRepository.cs:31`) porównuje wyłącznie `group.InstructorId`. Zastępca widzi termin
w `/api/schedule` (bo `SessionService` sprawdza też `SubstituteInstructorId`), ale **nie widzi
go w Kalendarzu**. Niespójność dwóch widoków tego samego grafiku.

### 3.3 Wielokrotne ładowanie całych tabel

Wzorzec „wczytaj wszystko i przefiltruj w pamięci” powtarza się w kilku miejscach:

- `SessionService.MakeupParticipantIdsForSessionAsync` i `MakeupSessionOptionsAsync` — każda
  wywołuje `groupRepository.ListAsync()` (wszystkie grupy z sesjami i obecnościami);
  jedno wejście na listę obecności potrafi zrobić to 3–4 razy,
- `ParentPortalService.GetPortalAsync` — wszystkie grupy + wszystkie lekcje + wszystkie faktury,
- `GroupService.GetSummariesAsync` — `GetByIdAsync(instructorId)` w pętli po grupach (N+1),
- `SessionService.LessonTitleMapAsync` — wszystkie lekcje razem z pełnym JSON-em konspektów,
  tylko po to, żeby wyciągnąć tytuł.

Przy kilkunastu grupach to niewidoczne. Przy 50+ grupach i pełnym roku terminów portal rodzica
i lista obecności będą zauważalnie mulić. Do zaadresowania, ale nie przed premierą.

### 3.4 Frontend w Dockerze ma zaszyty `http://localhost:5000`

`frontend/lesson-runner-web/Dockerfile` wykonuje `npm run build` bez `VITE_API_BASE_URL`, więc
`client.ts` wpada w fallback `http://localhost:5000`. Na maszynie developera działa (compose
wystawia API na 5000), ale **na dowolnym realnym serwerze frontend będzie strzelał do localhostu
przeglądarki**.

**Poprawka:** `ARG VITE_API_BASE_URL` w Dockerfile + `build.args` w compose, albo — czyściej —
proxy `/api` przez nginx (`nginx.conf` ma tylko fallback SPA) i ścieżki relatywne w kliencie.
Przy okazji rozwiązuje to CORS.

### 3.5 Polskie znaki — w obie strony

W tekstach widocznych dla użytkownika brakowało znaków diakrytycznych (zakładka Powiadomienia:
„Odswiez”, „Wyslij przypomnienia”, „Tresc wiadomosci”, „Podglad”; profil: „Zmiana hasla”,
„Uzyj obecnego hasla”). To łamie zasadę z `CLAUDE.md`.

Gorsza jest druga strona tego samego problemu: ktoś kiedyś puścił po repozytorium zbyt agresywne
find/replace, które **wstawiło ogonki tam, gdzie ich nie ma**. Ślady zostały w danych seed
i widać je w aplikacji:

- `"Dzieci mylą kategorie Zdarzenia **że** Sterowaniem"` — miało być „ze”,
- `"skroc **pokaż** do 10 s"` — rzeczownik „pokaz”, nie tryb rozkazujący,
- `"ruch **postaći**"`, `"nad **postaćia**"`, `"różne **odpowiedźi**"`,
- w kodzie Pythona dla dzieci: `**zadańia** = [...]`, `for **zadańie** in ...`,
- w `PLAN.md` konsekwentnie „instruktóra” zamiast „instruktora”.

Sama automatyczna podmiana słownikowa tego nie naprawi — te przypadki wymagają kontekstu.

**Poprawka:** przejście po `LessonSeedData.cs` i plikach UI (zrobione), plus test
`polishDiacritics.test.ts`, który skanuje źródła frontendu i wywala się na obu rodzajach błędów.
Lista kontrolna w teście jest jednocześnie dokumentacją tego, czego pilnujemy.

### 3.6 Rozjazd dokumentacji

`PLAN.md` (snapshot z ~14.06) opisuje system znacznie uboższy niż faktyczny stan —
nie ma tam kursów, płatności, powiadomień, kalendarza, audytu, portalu rodzica ani roli `Parent`.
Aktualny jest `PROJEKT_W_TRAKCIE` (10.07), ale i on nie zawiera ostatniej migracji
`AddGroupMeetingUrl` (23.07). `README.md` nadal opisuje `POST /api/auth/register`, który
został usunięty. Przy trzech osobach w projekcie to gwarantowane nieporozumienia.

## 4. Czego brakuje do prowadzenia zajęć online dla dzieci

Stan wyjściowy jest dobry: role `Admin` / `Instructor` / `Parent` istnieją, portal rodzica działa
i pokazuje harmonogram, link do spotkania, frekwencję i rozliczenia. Poniżej to, czego brakuje,
w kolejności realnej ważności.

### Priorytet 1 — bez tego portal rodzica nie domyka obietnicy

**a) Materiały do pobrania dla rodzica/dziecka.** To jedyna rzecz z Twojego opisu, której nie ma.
Model już to niesie: `LessonProjectFiles` (starter/final, np. `.sb3`) plus endpoint
`/download/lesson-files/{token}`, ale `ParentPortalDto` w ogóle nie zawiera materiałów. Potrzeba:

- pole „materiały dla rodzica” na poziomie lekcji lub terminu (świadomie oddzielone od notatek
  instruktora — te nie mogą wyciec),
- flaga „udostępnij po zajęciach” (materiał widoczny dopiero gdy termin ma status `Completed`),
- sekcja „Materiały” w `ParentPortalPage` z pobieraniem przez autoryzowany endpoint.

**b) Link do spotkania na poziomie terminu, nie tylko grupy.** Dziś `MeetingUrl` siedzi na
`Group`. Jedno zastępstwo (inny pokój Zoom prowadzącego), jedne zajęcia odrabiane w innym
terminie czy jednorazowa zmiana platformy wymagają zmiany linku dla całej grupy.
Dodaj `ScheduledSession.MeetingUrl` jako nadpisanie z fallbackiem na grupę.

**c) Samodzielny reset hasła.** Dziś **każde** hasło ustawia ręcznie admin
(`POST /api/users/{id}/password`). Przy instruktorach to do przeżycia, przy trzydziestu rodzicach
to etat. Potrzeba: „nie pamiętam hasła” → token jednorazowy na e-mail → ustawienie nowego.
Infrastruktura mailowa (`IEmailSender`, szablony, log wysyłek) już jest — brakuje tylko przepływu.

**d) Zaproszenia dla rodziców.** Konto rodzica zakłada admin, potem ręcznie linkuje je z
uczestnikiem (`/api/parent-links`). Docelowo: admin wpisuje e-mail opiekuna przy dziecku →
system wysyła zaproszenie → rodzic sam ustawia hasło, a powiązanie tworzy się automatycznie.

### Priorytet 2 — jakość obsługi rodzica

**e) Zgłoszenie nieobecności przez rodzica.** Rodzic widzi harmonogram, ale nie może powiedzieć
„Kuba jutro nie będzie”. Dziś dzwoni. Przycisk „Zgłoś nieobecność” przy terminie + widoczność
tego zgłoszenia na liście obecności instruktora to mały feature o dużym wpływie operacyjnym.

**f) Informacja zwrotna o dziecku.** Portal pokazuje wyłącznie procent frekwencji. Rodzic płacący
za kurs programowania chce wiedzieć, **co dziecko zrobiło i jak sobie radzi**. Notatka
`ScheduledSession.InstructorNote` już istnieje, ale jest wewnętrzna i wspólna dla całej grupy.
Potrzebna krótka notatka per dziecko per zajęcia, z jawnym przełącznikiem „widoczna dla rodzica”.

**g) Nagranie z zajęć.** Przy zajęciach online to standardowe oczekiwanie („Kuba chorował, czy
możemy obejrzeć?”). Wystarczy pole `RecordingUrl` na terminie + wyświetlenie w portalu po
zakończeniu.

**h) Eksport kalendarza (ICS).** Subskrypcja terminów w Kalendarzu Google/Apple —
dla rodzica i dla instruktora. Tanie w implementacji, bardzo doceniane.

**i) Powiadomienie o zbliżających się zajęciach z linkiem.** Worker przypomnień działa
(`NotificationReminderWorker`, co 30 min), ale szablon nie zawiera zmiennej z linkiem do spotkania —
warto dodać `{{link}}` do kontekstu szablonu.

### Priorytet 3 — dojrzałość produkcyjna

**j) RODO w praktyce.** Zgody (`DataProcessingConsentAt`, `ImageConsentAt`) i anonimizacja
uczestnika są zaimplementowane — dobrze. Brakuje: eksportu danych dziecka na żądanie rodzica
(art. 15/20), polityki retencji (po ilu latach kasujemy archiwalnych uczestników), rejestru
czynności przetwarzania i informacji, że pliki z `/uploads` są dostępne po adresie URL (p. 2.1).

**k) Integracja z platformą wideo.** Dziś link wkleja się ręcznie. Docelowo API Zoom / Google Meet
/ Teams tworzące pokój przy generowaniu terminu — eliminuje najczęstszy błąd operacyjny
(nieaktualny albo zapomniany link).

**l) Testy API i CI.** Jest 122 testy backendu i 109 frontendu na poziomie serwisów i view-modeli,
ale ani jednego testu HTTP end-to-end. Punkty 1.1 i 1.2 z tego raportu wyłapałby jeden test
integracyjny na `WebApplicationFactory` (`Program` jest już `public partial` — infrastruktura
gotowa). Do tego GitHub Actions z `dotnet test` + `npm test` na każdy push.

**m) Strefy czasowe.** Model używa `DateTimeOffset`, więc podstawa jest zdrowa, ale nie ma pojęcia
strefy użytkownika. Przy zajęciach online z dziećmi z zagranicy (a to typowy scenariusz)
rodzic zobaczy godzinę w swojej strefie przeglądarki, podczas gdy grafik był planowany
w czasie polskim. Warto to przynajmniej opisać w UI („godzina polska”).

**n) Uruchamianie jedną komendą.** Wciąż otwarte z Waszego backlogu — dwa terminale to źródło
błędów przy wdrożeniu.

## 5. Sugerowana kolejność prac

1. `SessionService` — przenieść powiadomienia o nieobecności do zapisu obecności **(1.1)**.
2. Polityka `StaffOnly` na `/api/lessons`, `/api/schedule`, `/api/calendar` **(1.2)**.
3. `HasAnyAdminAsync` + ochrona ostatniego admina **(1.3)**.
4. Rate limiting logowania i ukrycie kont dev na ekranie logowania **(2.2, 2.4)**.
5. Sekrety poza `docker-compose`, `VITE_API_BASE_URL` w buildzie frontendu **(2.5, 3.4)**.
6. Testy integracyjne HTTP na `WebApplicationFactory` dla ścieżek autoryzacji **(4l)**.
7. Materiały dla rodzica + link na poziomie terminu **(4a, 4b)**.
8. Reset hasła i zaproszenia dla rodziców **(4c, 4d)**.
9. Reszta: zgłaszanie nieobecności, notatka o dziecku, nagrania, ICS **(4e–4h)**.
10. Uporządkować dokumentację — `PLAN.md` do archiwum, jeden aktualny plik statusu **(3.5)**.
